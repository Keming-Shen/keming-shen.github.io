Linux服务器使用Codex CLI：安装、认证与自动化

发表于2026-09-20|更新于2026-10-09|「Linux」服务器操作指南
|浏览量:

Codex CLI 在终端中读取项目、修改代码并调用本机工具。通过 SSH 登录 Linux 服务器后运行 Codex，文件操作和命令执行发生在服务器，模型请求也由服务器发出。

本文使用普通 Linux 账户和 Bash，示例项目位于 ~/projects/demo。远程连接与整体工作流见 AI Coding指南；Claude Code 与 cc-switch 的配置见 Linux服务器安装Claude Code教程。

1 运行前需要准备什么

服务器需要能够访问安装文件、认证服务与模型接口。PC 浏览器能够联网，并不代表服务器上的命令行工具已经具备相同的访问条件。

使用官方模型服务时，不需要在服务器上下载模型权重，也不要求本机 GPU 用于模型推理。项目中的测试、数据处理和训练仍会占用服务器资源。

5 沙箱与审批各自控制什么

沙箱控制命令能够访问和修改的范围，审批策略控制何时需要进一步授权。 二者不是同一个开关。

  • read-only 用于读取和分析；需要写文件、缓存或构建产物的命令可能被阻止。
  • workspace-write 允许在工作区内写入，适合修改代码并运行必要检查。
  • on-request 表示由 Agent 在需要时请求审批，并不意味着每条命令都要确认。

工作区沙箱默认限制命令联网。这里说的是 Codex 调用的命令及其子进程，Codex 自身与模型服务的通信仍需要网络。下载依赖、访问外部服务等操作可能触发额外审批。

在交互界面中可用 /permissions 查看或调整权限。具体模式见 Codex 沙箱与审批说明。

权限范围也不等于资源预算。允许执行 Python，并不表示一次完整训练在时间、显存或数据访问方面都适合运行。任务中应明确样本范围、允许执行的检查和需要保留的输出。

codex exec 用于非交互执行，适合重复的代码检查、日志归纳和文档整理。默认要求工作目录位于 Git 仓库内。

--output-last-message 由 CLI 将最终回答保存到指定文件，区别于让 Agent 在沙箱中编辑项目。上例中的 mkdir 也由当前 Shell 提前执行。重复使用同一个输出路径会覆盖上次报告，需要保留历史时可更换文件名。

默认情况下，过程信息输出到标准错误，最终回答输出到标准输出。需要机器处理完整事件流时，可使用 --json；仅保存结论时，--output-last-message 更直接。

执行失败、输入日志不完整或指标定义不一致时，报告不应当作有效实验结论。流程中涉及数值汇总的部分，可由已经验证的脚本完成，再让 Codex 解释脚本输出。

非交互执行复用已有认证。定时任务或 CI 中的密钥应来自受控凭据存储，避免写入仓库脚本；权限应在调用时明确设置。参数及自动化认证说明见 Codex 非交互模式。

8 断线与常见问题

需要保持终端会话时，可先在服务器创建 tmux 会话，再进入项目启动 Codex：

tmux 需要事先安装。按 Ctrl+B，松开后按 d，可离开会话；重新 SSH 登录后用 tmux attach -t coding 接回。完整操作见 Linux服务器使用tmux管理长任务。

tmux 保留远端进程，但不能保证模型接口一直可用，也不会替代待处理的审批。若代理出口来自 PC 的 SSH 转发，PC 断线后代理也会失效；长时间调用 API 需要稳定的服务器网络出口。

常见问题可按发生阶段定位：

  • 安装或更新失败：检查下载地址连通性、磁盘空间和 CPU 架构，保留完整报错。
  • 认证失败：检查当前认证方式、账户权限和认证服务网络；程序已安装不代表已经登录。
  • 能聊天但无法运行命令：查看沙箱拒绝原因，区分目录权限、网络权限和项目依赖缺失。
  • 找不到 Python 或导入失败：在启动 Codex 的终端检查解释器与项目环境，见 Linux服务器Python环境管理。
  • 工作目录不对：退出并切换到目标仓库重新启动，避免把个人主目录当成整个项目工作区。
